# 📄 Database Design

# Spotinder

This document describes the database design for Spotinder, including the core entities, relationships, and the reasoning behind each table.

---

# 🎯 Database Goals

The database is intentionally lightweight.

Spotify already manages music metadata such as artists, albums, tracks, playlists, and audio features.

Spotinder only stores application-specific data that cannot be retrieved from Spotify.

The goals are:

- Store user interactions
- Store discovery preferences
- Track user activity
- Support analytics and insights
- Avoid unnecessary data duplication

# 🔑 Primary Keys

All entities use **UUIDs** as primary keys.

Advantages:

- Globally unique identifiers
- Better security than incremental IDs
- Easier future migration to distributed systems
- Prevents resource enumeration

---

# 👤 User

Represents an authenticated Spotify user.

```text
User

id (UUID)

spotify_id

display_name

email

avatar_url

country

product

adventure_level

blind_mode_default

created_at

updated_at
```

## Purpose

Stores user-specific information required by Spotinder.

Authentication remains handled entirely by Spotify OAuth.

Passwords are never stored.

---

# ❤️ Swipe

Represents every swipe performed by a user.

```text
Swipe

id (UUID)

user_id

spotify_track_id

direction

blind_mode

created_at
```

## Purpose

The Swipe table powers:

- Recommendation history
- User preferences
- Listening insights
- Discovery statistics

---

# 📅 Discovery Session

Represents one discovery session.

```text
DiscoverySession

id (UUID)

user_id

started_at

ended_at

songs_seen

songs_liked

blind_mode

adventure_level
```

## Purpose

Allows Spotinder to generate meaningful analytics such as:

- Session duration
- Songs explored
- Like ratio
- Discovery score
- Listening habits

---

# 🎵 Playlist

Represents playlists created through Spotinder.

```text
Playlist

id (UUID)

user_id

spotify_playlist_id

name

generated_by_ai

created_at
```

## Purpose

Stores references to playlists generated by Spotinder.

The playlist itself remains hosted on Spotify.

---

# 🎼 PlaylistTrack

Associates Spotify tracks with Spotinder playlists.

```text
PlaylistTrack

playlist_id

spotify_track_id
```

## Purpose

Maintains the relationship between playlists and the tracks selected for them.

# 🎵 Spotify as the Source of Truth

Spotinder intentionally does **not** duplicate Spotify's catalog.

The following data is always retrieved directly from the Spotify Web API:

- Artists
- Albums
- Tracks
- Genres
- Audio Features
- User Library
- Spotify Playlists

Only Spotify identifiers are stored whenever references are needed.

This approach keeps the database lightweight while ensuring that Spotinder always reflects Spotify's latest catalog.

---

# 🚫 Data We Do Not Store

The following entities are intentionally excluded:

- Artist
- Album
- Track
- Genre
- Audio Features
- Spotify Recommendations

These resources already exist within Spotify and would introduce unnecessary duplication.

---

# 📈 Future Database Extensions

As Spotinder evolves, additional entities may be introduced:

- AI Recommendations
- Daily Discovery
- User Achievements
- Listening Goals
- Mood History
- Social Features

These are intentionally excluded from the MVP to keep the initial implementation focused and maintainable.

---

# 💡 Design Philosophy

The database is designed around one principle:

> Store only what Spotinder owns.

Everything related to music metadata remains Spotify's responsibility.

Spotinder focuses exclusively on user interactions, preferences, and the personalized discovery experience.


# 📐 Naming Conventions

The project follows these conventions:

- Singular table names (`User`, `Swipe`, `Playlist`)
- UUID primary keys (`id`)
- Foreign keys use `<entity>_id`
- Timestamps use `created_at` and `updated_at`
- Enumerations are stored as strings where appropriate
